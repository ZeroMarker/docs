# 幂等：从数学到可靠 API

幂等（Idempotency）指一个操作执行一次与重复执行多次，产生的预期效果相同。它允许系统在网络超时、重复提交和消息重投时安全重试，是可靠 API 与分布式任务处理的重要基础。

## 数学中的幂等

如果函数满足 `f(f(x)) = f(x)`，那么这个函数就是幂等的。例如：

- 取绝对值：`abs(abs(-5)) = abs(-5) = 5`。
- 集合去重：对已经去重的集合再次去重，结果不变。
- 布尔运算：`A ∧ A = A`、`A ∨ A = A`。

## HTTP API 中的幂等

HTTP 中的幂等性关注重复相同请求对服务端的**预期效果**，不要求每次响应内容、状态码或日志完全相同。例如，第一次删除成功后返回 `204`，再次删除返回 `404`，仍可满足幂等语义：目标资源都已不存在。服务端也可以为每次请求分别记录访问日志。参见 [RFC 9110 §9.2.2](https://www.rfc-editor.org/rfc/rfc9110.html#section-9.2.2)。

| HTTP 方法 | 是否幂等 | 说明 |
|-----------|----------|------|
| GET | 是 | 读取资源；安全方法，不请求改变资源状态 |
| HEAD | 是 | 获取响应头；安全方法 |
| OPTIONS | 是 | 查询通信选项；安全方法 |
| TRACE | 是 | 请求诊断回环；安全方法 |
| PUT | 是 | 用请求中的表示创建或替换目标资源状态 |
| DELETE | 是 | 删除目标资源，重复请求的预期效果相同 |
| POST | 无幂等保证 | 重复提交可能创建多个资源，可通过业务设计实现幂等 |
| PATCH | 无幂等保证 | 是否幂等取决于补丁操作的具体语义 |

以上是 HTTP 方法的语义约定，服务端实现也必须遵守约定；仅把接口命名为 `PUT` 并不能自动获得幂等性。PATCH 可以设计为幂等，例如设置字段为固定值；累加数值、向数组末尾追加元素则通常不幂等。参见 [RFC 5789 §2](https://www.rfc-editor.org/rfc/rfc5789.html#section-2)。

### 非幂等：增加余额

```http
POST /accounts/123/increment
Content-Type: application/json

{
  "amount": 100
}
```

如果没有额外的去重机制，调用三次会使余额增加 300。

### 幂等：设置余额

```http
PUT /accounts/123/balance
Content-Type: application/json

{
  "balance": 1000
}
```

这里将余额建模为独立资源，重复请求都是把它设置为 1000。在没有其他并发写入的情况下，执行一次与多次的最终余额相同。

这是说明语义的简化示例。幂等性本身不解决并发更新冲突；如需避免覆盖他人的修改，可以另外使用版本号或 `ETag` 与 `If-Match` 条件请求。

## 支付系统中的幂等键

支付请求可能已经成功，但客户端因为网络超时没有收到响应。此时直接重新提交，可能重复扣款。常见设计是让同一笔业务操作在重试时复用一个 `Idempotency-Key`：

```http
POST /payments
Content-Type: application/json
Idempotency-Key: order-20261111-001

{
  "amount": 100,
  "currency": "USD"
}
```

这里的键与字段仅用于展示接口设计；金额单位、键的作用域和有效期由具体 API 约定。

服务端处理流程：

1. 按调用方、操作类型和幂等键定位记录，并校验请求参数是否一致。
2. 对新键，原子地创建“处理中”记录，取得执行资格。
3. 执行业务操作，持久化业务结果与幂等记录。
4. 对已完成的重复请求，返回已保存的结果，不再次扣款。
5. 对仍在处理中的重复请求，按接口约定等待或返回处理中状态。

“检查键 → 扣款 → 保存结果”只是概念流程，直接分开执行会留下故障窗口：两个并发请求可能同时通过检查；扣款后进程崩溃也可能导致结果尚未保存。

实现时需要处理这些边界：

- **并发去重**：用数据库唯一约束、事务或原子写入竞争同一键，避免先查后写的竞态。
- **参数一致性**：同一键对应不同金额或收款人时应拒绝，不能直接复用旧结果。
- **故障恢复**：本地业务写入与幂等记录尽量在同一事务内提交；涉及外部支付渠道时，应向渠道传递稳定的幂等标识，并通过查询、对账等机制恢复不确定状态。
- **重试与有效期**：同一业务操作重试时复用原键；新操作使用新键。保留时间必须覆盖业务重试窗口，记录过期后的去重保证需要明确约定。
- **失败结果**：区分尚未执行、已明确失败和结果未知；不能在结果未知时盲目重新扣款。

幂等键只是标识，可靠性来自它背后的原子性、持久化与恢复机制。

## 分布式系统中的应用

| 场景 | 幂等处理思路 |
|------|--------------|
| 支付系统 | 同一支付操作复用业务标识，避免重复扣款 |
| 数据库写入 | 对业务唯一键建立约束，避免重复创建记录 |
| 消息队列 | 记录消息 ID，并将去重记录与业务写入放在同一事务中 |
| 任务调度 | 按任务实例标识去重，或将任务设计为设置目标状态 |
| API 服务 | 通过固定资源标识或幂等键安全处理重复请求 |

消息消费中，仅先检查“是否消费过”再修改数据，同样存在并发和崩溃窗口。外部邮件、通知等副作用也需要单独考虑，不能仅凭数据库事务就认为整个链路已经幂等。

## 幂等不等于只执行一次

| 概念 | 关注点 |
|------|--------|
| 幂等（Idempotency） | 允许重复调用，但预期业务效果与一次相同 |
| 至少一次（At-least-once） | 在保证范围内至少投递或处理一次，允许重复 |
| 恰好一次（Exactly-once） | 需明确保证范围：可能指消息处理、事务提交或可观察的业务效果，并不总表示底层代码只运行一次 |

工程上常用“至少一次投递 + 幂等处理”实现业务效果去重。例如，同一条扣款消息可能被投递和处理多次，但账本中只产生一笔有效扣款。

这并非无条件的等式：去重标识必须稳定，记录必须可靠保存，业务写入与去重之间必须有一致性保证，外部副作用也必须纳入设计。在这些条件成立的范围内，才能实现恰好一次的业务效果。
