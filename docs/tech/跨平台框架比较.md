# 跨平台框架比较

> 更新：2026 年 11 月。本文讨论应用开发框架，比较 Android、iOS、Windows、macOS、Linux、浏览器与小程序；具体系统版本、框架版本与插件支持以官方文档为准。

“一套代码多端运行”可以指共享业务逻辑、共享界面、将 Web 页面放进应用容器，或把页面编译到不同的小程序平台。这些方式的开发成本、平台体验和维护边界不同。选型前，先确定必须交付的平台，再确认哪些代码确实需要共享。

## 先确定共享到哪一层

| 共享层次 | 共享什么 | 常见做法 | 仍然需要平台实现 |
| --- | --- | --- | --- |
| 业务逻辑 | 网络、数据模型、校验、状态与规则 | Kotlin Multiplatform、.NET 类库、TypeScript 包 | 存储、权限、后台任务、系统集成 |
| 界面与交互 | 页面、组件、导航、样式 | Flutter、React Native、.NET MAUI、Compose Multiplatform、WebView | 平台手势、输入法、弹窗、无障碍细节 |
| 应用容器 | 把 Web 页面装进安装包 | Electron、Tauri、Capacitor | 窗口、菜单、通知、文件系统、签名 |
| 编译目标 | 一套源码编译到不同端 | uni-app、Taro、Flutter Web / Wasm | 小程序 DSL、各平台组件与 API 差异 |

共享层次越多，重复开发通常越少，但平台差异也会集中到框架层。实际项目往往同时采用几种方式：共享业务逻辑，界面部分共享，少数关键页面用原生实现。选型时要问的不是“能不能一套代码”，而是“哪些代码共享后仍然可控”。

## 主要方案一览

| 方案 | 主要语言与界面方式 | 主要交付平台 | 适合的起点 | 需要留意 |
| --- | --- | --- | --- | --- |
| [Flutter](https://docs.flutter.dev/reference/supported-platforms) | Dart；框架自行绘制大部分界面 | Android、iOS、Windows、macOS、Linux、Web | 新项目要在多端保持统一界面 | Web 以画布渲染为主，DOM、SEO、文本选择与无障碍需单独验证；原生能力仍要检查插件 |
| [React Native](https://reactnative.dev/docs/intro-react-native-components) | JavaScript / TypeScript；使用平台原生视图 | Android、iOS 为核心；Web、Windows、macOS 依赖独立项目 | React 团队开发移动应用 | 扩展平台的发布节奏与核心不同；新架构下仍需核对原生库兼容性 |
| [Kotlin Multiplatform](https://kotlinlang.org/docs/multiplatform/kmp-overview.html) | Kotlin；可只共享逻辑，也可配合 Compose Multiplatform 共享界面 | Android、iOS、桌面、Web，取决于所选目标和 UI 方案 | 已有原生应用，想逐步复用逻辑 | 共享层越大，跨平台依赖与平台差异处理越多；Compose Multiplatform 的 Web 目标仍为 Beta |
| [.NET MAUI](https://learn.microsoft.com/dotnet/maui/) | C# / XAML；映射到平台控件 | Android、iOS、Windows、macOS（Mac Catalyst） | .NET 团队开发移动和桌面应用 | Linux 和浏览器不是其官方标准应用目标；复杂控件常需 handler 或平台代码 |
| [Electron](https://www.electronjs.org/docs/latest/) | HTML / CSS / JavaScript；内置 Chromium 与 Node.js | Windows、macOS、Linux | 已有 Web 团队，需要成熟的桌面应用方案 | 每个应用附带浏览器运行时，须测量包体和内存；主进程与渲染进程的安全边界要设计 |
| [Tauri 2](https://tauri.app/start/) | Web 前端；系统 WebView 与 Rust 核心 | Windows、macOS、Linux；也可面向 Android、iOS | Web 团队重视桌面包体，愿意处理 Rust 与系统集成 | 不同系统的 WebView 需分别测试；移动端能力与插件仍需逐项验证 |
| [Capacitor](https://capacitorjs.com/docs) | HTML / CSS / JavaScript；移动端 WebView 与原生插件 | Android、iOS，并可复用 Web 应用 | 已有网站或 Web 应用要进入应用商店 | 对复杂原生交互、动画或设备 API，要验证插件和实际体验；桌面端不是其官方目标 |
| [uni-app](https://uniapp.dcloud.net.cn/tutorial/) | Vue / JavaScript；按目标平台编译，App 常规 `.vue` 页面由 WebView 渲染 | 各类小程序、Web、Android、iOS；其他目标以文档为准 | Vue 团队以小程序为重点，同时交付 H5 与 App | 普通 Web 的 DOM 库未必能用于小程序；App 页面渲染方式与 uni-app x 有区别 |
| [Taro](https://docs.taro.zone/) | React / Vue 等；面向不同小程序和 H5 转换 | 各类小程序、H5；可通过 React Native 路径开发 Android / iOS App | React 团队以多种小程序为重点 | App 端需额外适配 React Native；组件与 API 的多端支持需逐项核对 |

表中“主要交付平台”描述的是官方文档中的常见目标，并不表示同一套界面、插件与发布流程在所有平台完全一致。例如 React Native 的 Web 和桌面支持属于独立维护的扩展平台；Compose Multiplatform 的共享界面是可选方案，其 Web 目标基于 Kotlin/Wasm，截至本文更新时仍标为 Beta。参见 [React Native 扩展平台](https://reactnative.dev/docs/out-of-tree-platforms)、[Kotlin Multiplatform 官方说明](https://kotlinlang.org/multiplatform/)和 [Compose Multiplatform 平台状态](https://kotlinlang.org/compose-multiplatform/)。

**uni-app 与 Taro 的位置**：两者更强调小程序与 H5 的多端交付。uni-app 采用 Vue 风格页面和统一 API，常规 App `.vue` 页面通常经 WebView 渲染；[uni-app x](https://doc.dcloud.net.cn/uni-app-x/) 是另一个技术路线，提供原生渲染，不能把两者的性能与兼容性混作一项。Taro 可使用 React 或 Vue 开发小程序与 H5；其 [Android / iOS App 路径](https://docs.taro.zone/docs/react-native)基于 React Native，需要相应的工程配置和平台适配。两者都应按目标小程序逐项检查组件与 API 支持，不能因为语法接近 Web 就假设现成网页可以直接编译。

## 五种技术形态

跨平台框架的差异，很大程度上来自“界面由谁绘制、代码运行在哪里”。按界面渲染与运行方式可以分成五类：

| 形态 | 代表 | 界面一致性 | 平台观感 | 主要成本 |
| --- | --- | --- | --- | --- |
| 自绘引擎 | Flutter、Compose Multiplatform | 高 | 需主动适配平台习惯 | 引擎与字体包体、无障碍语义、文本输入细节 |
| 平台原生控件 | React Native、.NET MAUI | 中 | 高 | 平台差异、桥接层与控件映射 |
| 捆绑浏览器 | Electron | 高（Web 技术） | 桌面 Web 应用感 | 固定运行时、内存与多进程管理 |
| 系统 WebView | Tauri、Capacitor、uni-app App | 高（Web 技术） | 取决于页面实现 | WebView 版本差异、首屏与设备能力 |
| 小程序编译 | uni-app、Taro | 受目标平台限制 | 平台组件观感 | 各小程序 API、组件与审核规则差异 |

### 自绘界面

Flutter 由框架绘制大部分控件，界面在不同系统上更容易保持一致；代价是平台细节要由框架或业务代码补齐，例如返回手势、文本选择菜单、输入法行为、系统字体缩放和无障碍朗读。Flutter 在 iOS 上使用 Impeller 渲染，Android 与桌面端的默认渲染路径随版本推进，具体以发行说明为准。参见 [Flutter 架构](https://docs.flutter.dev/resources/architectural-overview)。

Compose Multiplatform 同样以自绘为主，但它的独特之处是可与 Kotlin Multiplatform 的逻辑共享配合，也允许在 iOS 上逐步替换或嵌入 SwiftUI / UIKit 界面。其 iOS 与桌面目标已稳定，Web 目标仍处于 Beta，适合已有 Kotlin 体系的团队分阶段推进。

### 平台原生控件

React Native 和 .NET MAUI 把组件映射到平台控件。这样按钮、列表、输入框更容易继承系统行为，系统升级带来的新外观也可能自动生效；但同一段界面代码在不同平台上的布局、字体和交互未必一致，复杂定制往往要写平台代码。React Native 的新架构已取代旧的桥接模式成为主要路径，原生模块与视图组件需要按新架构检查兼容性。参见 [React Native 新架构说明](https://reactnative.dev/blog/2024/10/23/the-new-architecture-is-here)。

.NET MAUI 通过 handler 把控件映射到 Android、iOS、Mac Catalyst 与 Windows 的原生实现。它适合已经使用 C#、.NET 类库和 Visual Studio 的团队；如果还要覆盖 Linux 或浏览器，需要另选目标或采用非官方方案。Blazor Hybrid 可以在 MAUI 中承载 Web 界面，但它仍然依赖 WebView，不能等同于“原生渲染”。

### WebView 容器

Electron 在应用内捆绑 Chromium 与 Node.js，因此渲染结果和浏览器能力较可控，代价是每个应用都带一份运行时，安装包、内存和多进程管理成本较高。它的优势在于成熟：窗口、菜单、托盘、自动更新、崩溃报告和原生模块都有大量现成方案。安全上应使用 `contextIsolation`、沙箱、受限的 preload 脚本与明确的 IPC 白名单，不宜把 Node.js 能力直接暴露给页面。

Tauri 使用系统 WebView（Windows 的 WebView2、macOS 的 WKWebView、Linux 的 WebKitGTK），应用本体通常更小，但必须面对不同系统 WebView 版本的差异。它的核心用 Rust 编写，前端通过命令与插件访问系统能力；移动端支持通过插件体系提供，并非所有官方插件都覆盖移动平台，需要按项目核对。参见 [Tauri 进程模型](https://tauri.app/concept/process-model/)和 [Tauri 移动端说明](https://v2.tauri.app/develop/)。

Capacitor 把 Web 应用放入 Android / iOS 的 WebView，再通过插件桥接设备能力。它适合已有 Web 产品快速进入应用商店，尤其是表单、内容、后台管理类界面；但复杂手势、长列表、动画和高频设备调用仍要实测。Capacitor 8 的最低支持范围为 iOS 15 与 Android 7（API 24），升级前应核对插件与构建工具链。参见 [Capacitor 支持策略](https://capacitorjs.com/docs/main/reference/support-policy)。

### 小程序编译

uni-app 与 Taro 把受约束的页面代码编译到不同小程序和 H5。它们共享的是符合框架规范的页面与逻辑，不是任意 Web 页面；小程序的组件、样式能力、路由和 API 都与浏览器不同。App 端还要区分 WebView 渲染与原生渲染两条路线。选择这类方案时，应先把目标小程序列全，再逐个确认登录、支付、地图、文件、订阅消息等能力。

## 关键维度

### 视觉一致性与平台规范

“一致”是产品决策，不是框架的自动结果。自绘方案容易做到像素级一致，但如果完全忽略平台习惯，用户会觉得应用“不像这个系统”；原生控件方案更容易获得平台观感，却可能出现双端布局和交互不一致。WebView 方案可以复用设计系统，但滚动、日期选择、键盘避让、返回手势和弹窗样式仍由宿主环境决定。

比较时建议分别列出：

- 必须统一的品牌视觉：颜色、字体、图标、组件形状。
- 应遵循平台习惯的部分：导航、返回、权限弹窗、分享、支付、设置入口。
- 需要单独设计的部分：平板、折叠屏、桌面窗口、键盘与鼠标、触控笔。

无障碍也应纳入同一张表。原生控件通常自带较多语义；自绘界面需要框架提供语义树并逐页验证；WebView 界面则取决于 Web 无障碍实现。三者都不能仅凭框架宣传判断合规。

### 性能：先定义指标

这些架构差异不能直接换算成“性能排名”。启动时间、滚动流畅度、安装包、空闲内存和电池消耗取决于业务代码、依赖、设备及构建配置。应以同一功能、同一设备和正式构建做对比。

| 指标 | 关注点 | 常见测量方式 |
| --- | --- | --- |
| 冷启动 | 进程创建、引擎初始化、首屏数据 | Android `am start -W`、Xcode Instruments、桌面端进程计时 |
| 首屏可交互 | 字体、图片、列表与 hydration | 系统 trace、框架性能面板、打点 |
| 滚动与动画 | 掉帧、长列表回收、图片解码 | 帧耗时工具、慢速设备实机录屏 |
| 内存 | 空闲、峰值、多窗口、WebView 缓存 | Android Studio Profiler、Instruments、系统任务管理器 |
| 安装包 | 运行时、原生库、资源与字体 | Release 构建、按 ABI 拆分后对比 |
| 电量与后台 | 定时任务、定位、推送唤醒 | Battery Historian、系统能耗日志 |
| Web 首屏 | 资源下载、Wasm 编译、缓存命中 | 浏览器 Performance 面板、真实网络限速 |

React Native 的新架构减少了旧桥接的序列化开销，但 JavaScript 线程、原生视图数量和第三方库仍会影响体验；Flutter 的自绘引擎能减少控件映射差异，但引擎启动、着色器与图片解码仍有成本；Electron 的 Chromium 启动和内存是固定基线；Tauri 与 Capacitor 的 WebView 冷启动则受系统环境影响。任何一项都应在目标低端设备上测，而不是只看开发机。

### 包体与内存

安装包大小和运行时内存是两件事。Electron 自带 Chromium，安装包和空闲内存有明显固定成本；Tauri 的安装包通常更小，但依赖系统 WebView，Linux 发行版与 Windows 旧环境可能缺少或滞后于所需版本。Flutter 需要携带引擎与字体资源，可通过拆分 ABI、裁剪图标和资源控制体积。React Native 使用 Hermes 字节码并携带原生库，新架构的 C++ 代码生成也会影响体积。Capacitor 的体积主要是 Web 资源加原生壳，业务页面越大，差距越接近普通 Web 应用。

多窗口、托盘常驻、后台同步和自动更新会显著改变内存与磁盘占用。评估时应分别测“首次安装”“空闲”“打开主界面”“长时间使用”四种状态，并把自动更新包与缓存计入总占用。

### 原生能力接入

所有跨平台方案都提供“逃生通道”，区别在于通道的成本和稳定性：

| 方案 | 原生扩展方式 | 需要重点核对 |
| --- | --- | --- |
| Flutter | Platform Channel、FFI、联邦插件 | 插件是否支持目标平台与新系统版本 |
| React Native | 原生模块、TurboModules、Fabric 组件、JSI | 新架构兼容性、C++ 与平台代码维护 |
| Kotlin Multiplatform | `expect` / `actual`、cinterop、Swift / Objective-C 互操作 | 共享层边界、iOS 内存与线程模型 |
| .NET MAUI | Handler、平台特定代码、绑定库 | 控件映射、平台 API 覆盖、Linux 缺口 |
| Electron | Node.js 原生模块、IPC、预加载脚本 | 安全边界、原生模块 ABI、签名与公证 |
| Tauri | Rust 命令、插件、权限能力配置 | 移动端插件覆盖、系统 WebView 差异 |
| Capacitor | 原生插件、Web 桥接 | 插件维护状态、复杂交互与性能 |

“插件市场里有很多插件”不等于项目所需能力可用。至少要检查：最近一次发布、未解决的关键 issue、目标平台覆盖、是否支持新架构或新系统、许可证、二进制体积，以及 iOS 隐私清单与 Android 16 KB 页面大小等发布要求。相机、蓝牙、地图、支付、推送、后台任务、桌面小组件、分享扩展和手表应用，通常是最容易暴露差距的部分。

### Web、桌面与移动的覆盖边界

“支持某个平台”与“在该平台适合生产使用”是两件事：

- React Native 的 Web、Windows、macOS 支持来自独立项目，版本节奏与核心不同，不能假设一次升级全部同步。
- Flutter 的 Web 构建以 Canvas / Wasm 渲染为主，Chromium 较新版本可默认使用 Wasm，WebKit 与 Gecko 可能回退到 JavaScript 渲染；SEO、文本选择、浏览器扩展与部分无障碍能力需要专门处理。参见 [Flutter WebAssembly 支持](https://docs.flutter.dev/platform-integration/web/wasm)。
- Compose Multiplatform 的 Web 目标仍为 Beta，适合试验或内部工具，不应直接等同于移动端成熟度。
- .NET MAUI 的官方目标不含 Linux 与浏览器；如有这些需求，应把它们视为独立交付目标。
- Tauri 的桌面端成熟度高于移动端；移动端能力依赖插件，复杂应用需要预留原生开发。
- Capacitor 官方聚焦 Android / iOS；桌面端通常需要另配 Electron、Tauri 或原生外壳。

如果产品同时需要内容型网站和应用商店客户端，通常应分别验证 Web 体验与应用体验。“能运行在 Web”不等于适合搜索、无障碍或内容型网站；也不保证移动端手势与导航自然。

### 团队、工具链与维护

框架选型也是团队选型。应比较：

- **语言与招聘**：Dart、Kotlin、C#、TypeScript、Rust 的团队储备与学习成本。
- **调试与热重载**：是否能复现平台问题，是否能在不重启的情况下修改界面与逻辑。
- **构建与发布**：iOS 签名通常需要 macOS / Xcode 环境；桌面端涉及代码签名与公证；Android 需要 SDK、NDK 与目标 API 管理。
- **测试矩阵**：双端加桌面、平板、折叠屏、旧系统与低端设备后，测试成本可能超过共享代码节省的成本。
- **升级节奏**：Flutter 按季度发布，React Native 与 Electron 节奏更快，.NET 按年度大版本推进；升级窗口应纳入维护计划。
- **代码组织**：共享模块、平台适配层、设计系统与业务页面如何分仓或分目录，决定后续能否独立演进。

### 安全与发布合规

WebView 容器和跨平台插件会扩大攻击面。Electron 应限制 Node.js 暴露、启用上下文隔离与沙箱、设置 CSP，并校验 IPC 消息；Tauri 应使用权限能力配置，避免把任意命令开放给前端；Capacitor 与 uni-app 应避免在 WebView 中加载不可信远程页面，并妥善处理深链与外部跳转。

发布侧还要核对：

- **应用商店规则**：动态下发代码或改变主要功能的更新，可能违反 Apple App Store 审核指南 3.3.2 等条款；热更新不能当作绕过审核的手段，需逐案评估。
- **iOS 隐私清单**：第三方 SDK 与自有代码的数据收集声明要完整。
- **Android 原生库**：面向新目标版本时，需确认 16 KB 页面大小等要求，尤其是 Flutter、React Native 与 Capacitor 插件中的 `.so` 文件。
- **桌面签名**：Windows 代码签名、macOS 公证与自动更新签名链要提前准备。

## 组合与迁移策略

多数长期项目不会只选一个框架，而是组合使用：

- **新移动项目、强调统一视觉**：Flutter 或 Compose Multiplatform 承担主要界面，支付、推送、相机等高风险能力保留原生实现。
- **React 团队、强调平台观感**：React Native 承担主流程，复杂页面或系统深度集成页面嵌入原生界面。
- **已有原生应用、先减少逻辑重复**：Kotlin Multiplatform 从网络、模型、校验等模块开始，界面继续使用 SwiftUI / UIKit 与 Jetpack Compose。
- **已有 Web 应用、要桌面客户端**：优先评估 Tauri 或 Electron；前者关注包体与系统 WebView 差异，后者关注运行时成本与原生集成成熟度。
- **已有 Web 应用、要移动安装包**：Capacitor 先验证插件与复杂交互；若体验差距明显，再把关键页面改为原生或改用其他框架。
- **.NET 团队、移动与 Windows 同时交付**：.NET MAUI 先验证控件映射与目标平台缺口，Linux / 浏览器需求单独规划。

迁移时应避免“一次性重写”。先划定共享边界，选择一个完整业务流程做原型，测量平台代码比例与构建时间，再决定是否扩大共享范围。

## 按场景选型

| 你的主要需求 | 优先验证 | 选择理由 |
| --- | --- | --- |
| 从零开发 Android 与 iOS，要求统一、可定制的视觉 | Flutter | UI 与逻辑可集中开发；先验证关键原生插件与无障碍 |
| Kotlin 团队要从共享逻辑走到共享界面 | Kotlin Multiplatform + Compose Multiplatform | iOS / 桌面界面已稳定，可与原生界面逐步混合 |
| React 团队开发移动应用 | React Native | 能沿用 React 知识和 JavaScript / TypeScript 工具链 |
| 已有 Android / iOS 原生应用，先减少业务逻辑重复 | Kotlin Multiplatform | 可逐模块接入，同时保留原有界面 |
| .NET 团队同时交付移动与 Windows / macOS 应用 | .NET MAUI | 沿用 C# 与现有 .NET 工程经验；Linux 与浏览器需另选 |
| 现有 Web 应用需要 Windows / macOS / Linux 客户端 | Electron 或 Tauri | 前者集成 Chromium，环境较一致；后者包体更小，但需验证系统 WebView |
| 现有 Web 应用需要 Android / iOS 安装包 | Capacitor | 复用页面与 Web 工具链，再以插件接入设备能力 |
| 桌面工具、内部管理端，Web 团队维护 | Tauri 或 Electron | 开发效率高；按包体、内存、系统集成与安全要求取舍 |
| Vue 团队要同时交付微信等小程序、H5 和 App | uni-app；如需原生渲染再评估 uni-app x | 小程序与 App 都在其目标范围，先核对实际所需 API 与页面渲染模式 |
| React 团队要交付多个小程序和 H5 | Taro | 保留 React 开发方式；若还要 App，单独验证 React Native 端 |
| 同时需要网站与应用商店客户端 | 分别验证 Web 体验和应用体验 | “可运行在 Web”不等于适合搜索、无障碍或内容型网站 |
| 高性能图形、游戏或重度实时渲染 | 游戏引擎或原生图形栈 | 通用 UI 框架不是为这类负载设计的；应先明确帧率与设备下限 |
| 只有一两个平台、界面简单、原生团队成熟 | 原生开发 | 跨平台框架的抽象与适配成本可能高于重复开发 |

## 常见误判

1. **“一套代码”等于“一份代码”**：共享的是框架允许共享的部分，平台适配、签名、测试与发布仍然存在。
2. **WebView 一定慢，自绘一定快**：体验取决于页面复杂度、启动路径、缓存和原生模块，必须实测。
3. **自绘界面自动一致**：字体、输入法、返回手势、权限弹窗和无障碍仍需平台适配。
4. **插件多就等于能力全**：关键插件可能长期未更新，或只支持部分平台与新架构。
5. **热更新可以绕过审核**：动态下发代码受商店规则限制，不能作为规避审核的方案。
6. **桌面端用 Web 技术就等于网站体验**：窗口管理、菜单、文件系统、快捷键和多显示器都要单独设计。
7. **框架升级没有成本**：大版本可能要求新工具链、新系统 SDK 或原生库迁移，应预留升级窗口。
8. **只计算开发成本**：测试矩阵、发布流水线、插件维护和平台适配往往才是长期成本的大头。

## 做决定前的验证清单

1. **平台边界**：列出必须支持的系统版本、设备形态和发布渠道；确认构建与签名所需的操作系统。例如 iOS 开发与签名通常需要 macOS / Xcode。
2. **关键能力**：用小型原型验证相机、蓝牙、地图、支付、推送、后台任务、深链、分享与文件访问等真正会用到的功能，而非只看插件列表。
3. **实际体验**：在低端设备和目标系统上测启动、内存、滚动、输入法、辅助功能与离线行为；桌面端还要测多窗口、菜单、快捷键和高分屏。
4. **工程链路**：验证 CI 构建、签名、公证、崩溃收集、日志、自动更新与商店提交流程，不只验证本地能跑。
5. **维护成本**：核对插件维护状态、升级频率、平台代码比例，以及团队熟悉的语言和调试工具。
6. **合规要求**：确认隐私清单、权限说明、数据安全表单、原生库页面大小与热更新策略符合目标商店规则。

可以用一张简单的评分表辅助讨论，但权重应按业务调整，并先设定“一票否决项”（例如必须支持某个设备能力、必须通过某平台审核）：

| 维度 | 示例权重 | 评分要点 |
| --- | --- | --- |
| 平台覆盖 | 20% | 目标系统、设备形态、Web / 桌面 / 小程序是否真实可用 |
| 关键能力 | 25% | 原型中高风险功能的通过率与原生扩展成本 |
| 体验与性能 | 20% | 冷启动、滚动、内存、包体与无障碍 |
| 团队与工具 | 15% | 语言储备、调试效率、招聘与学习成本 |
| 生态与维护 | 10% | 插件质量、社区活跃度、升级节奏与长期支持 |
| 发布与合规 | 10% | 签名、商店规则、隐私与安全边界 |

如果需求尚不明确，先做一个包含最难设备能力和一条完整业务流程的原型，再决定框架。跨平台方案降低的是一部分重复开发成本，并不会消除各平台的测试、适配和发布工作。
